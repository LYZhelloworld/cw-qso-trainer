# 开发路线（五步法）与平台选型

> 本项目的技术栈、平台决策、开发分期与后续计划。
> 策略：**自底向上、每层独立可验证**——先保证"大脑"（状态机）正确，再补输入（解码）、生成（HAM）、感知（音频）、外壳（UI）。
> 各能力域的设计见对应文档：[CW 编解码](./CW-PARSING.md)、[报文解析](./MESSAGE-PARSING.md)、[通联过程](./QSO-PROTOCOL.md)、[虚拟 HAM 策略](./VIRTUAL-HAM.md)、[音频与电磁环境](./AUDIO-ENVIRONMENT.md)、[界面](./UI.md)、[日志与存储](./LOG.md)。

---

## 平台与技术选型

> **结论（2026-10-14）**：目标产物是 **exe**，路线为 **Web 原型 → Tauri 2 打包 exe**（不用 PWA）。当前用**原生 TypeScript + Vite、零 UI 框架**直接操作 DOM；核心模块（状态机 / 解码 / HAM / 音频）不碰 DOM，这套代码可直接搬进 Tauri 的 WebView，迁移面最小。

| 平台 | 优势 | 劣势 |
|---|---|---|
| Web 原型 | 开发快、跨平台、离线可用；Tauri 迁移前可先做验收 | 页面失焦时无法捕获键盘；音频调度需 lookahead |
| Windows / Tauri（最终路线） | 全局键盘、音频延迟低、原生手感、可打包 exe | 需装 Rust 工具链（Windows 还需 VS 生成工具）；未签名 exe 有 SmartScreen 警告 |

- **PWA 不做**：既然目标是 exe，PWA 解决的"网页也能装到桌面"与之重复。
- **迁移成本在工具链，不在改代码**：Web Audio 与 IndexedDB 在 Tauri 的 WebView 里都可用；迁 Tauri 顺带解决全局快捷键与自动播放拦截。Windows 需 WebView2。
- **快捷键绑定**：Web / Tauri 都用 `KeyboardEvent.code` 绑物理键位；默认直键 `Space`，iambic 点键 `KeyZ`、划键 `KeyX`（相邻便于双桨同按，也不与浏览器快捷键冲突），均可在设置页改绑。已知限制：Web 页面失焦时捕获不到键盘（迁 Tauri 后解决）。

## 第一步：文本直通状态机原型

目标：用 CW 报文的字母文本与一个虚拟 HAM 完成通话，专门验证 QSO 状态机能否正确解析各种输入。

范围与约束：
- 频率固定（单频道）、时间固定（无随机延迟）
- 无任何电磁环境（无 QSB / QRM / QRN）
- 用户输入以字母文本形式直接喂入，绕过摩斯解码与音频
- 虚拟 HAM 用确定性脚本驱动（固定应答逻辑，不随机）

本步实际落地三件套（不只是状态机）：
- 数据层：`data/cty.dat` 解析 + 前缀 → 实体查表（展开 `prefixes`、多向前缀匹配）
- 报文解析：文本 → `ParsedMessage`（见 [报文解析](./MESSAGE-PARSING.md)）：CQ 去重、呼号 ITU 格式 + 前缀表校验、RST 整 token 校验、省略呼号判断、BK / PSE K 处理、用户输入宽容容错
- QSO 状态机：7 状态 + 转移，消费 `ParsedMessage`（见 [通联过程](./QSO-PROTOCOL.md)）

必须实现并测试的逻辑：
- 状态机本身对「超时」的确定性转移。当前实现分三层：**HAM 持续呼叫的节奏由波段层调度**（`ham/activity`，台不再有"3 分钟无应答下线"）；**用户与对方之间的等待由会话的两个时钟推进**（`src/ui/sessionPatience.ts`）——自己呼叫后频段安静满 15 秒即收回（`Patience.expireOwnCq`），对方发完一句等 10 秒、重发 2 次仍无人应即放弃（`Patience.servicePartnerWait`）；状态机只保留 `timeoutFirstCall` / `timeoutResend` / `hamOffline` 这三个确定性钩子作为语义接口，由上面两处以注入的时钟调用，不自己持有定时器。
- 因此「对方发完一句就等你」是有时间窗的：解析用户那一行的同时生成回复，随后由 `servicePartnerWait` 计时，超时重发、再超时结束这次通联。

测试用例（重点，验证"用户输入宽容"基线，参考真实 CW 通联）：
- 正常流：用户确认的 6 行序列（CQ → HAM 应答 → 用户 R+RST+BK → HAM R+RST+BK → 用户 R+TU73SK → HAM R+TU73SK）
- 异常流：抄错呼号（QRZ?）、RST 非法（UR RST?）、接收不全（? / AGN?）、K 与 BK 混用、呼号省略与误省、带 / 不带 R、CQ 三遍去重、操作后缀 /P /M /5、纯 K 结尾、SK 提前结束等

## 第二步：电键输入转文字（摩斯解码）

目标：实现摩斯解码，将用户电键（直键 / iambic / 键盘模拟）产生的点划时序转换为字母文本，接入第一步已完成的"文本 → 状态机"链路。

范围：
- 点划 / 时序 → 字母（见 [CW 编解码](./CW-PARSING.md) 的摩斯解码节：时序基准、符号判定、码表、容错）
- 支持 Farnsworth：放大字符 / 单词间隔而不改变点划基准速度
- 产出文本后，复用第一步的报文解析与状态机——第一步是第二步的上游依赖

边界：本步不涉及音频识别（用户键控直接产生时序事件，不经 FFT / 频谱）；音频渲染留到第四步。

## 第三步：多虚拟 HAM 与频率活动

目标：实现虚拟 HAM 的生成机制，让多个虚拟 HAM 在同一频率（及多个频率）上活动。

范围：
- 呼号生成（B?7 > B?? > 地理邻近 > 同洲 > 其他 的加权，见 [虚拟 HAM 策略](./VIRTUAL-HAM.md)）
- 运行时行为：CQ 节奏、应答延迟、接收不全（? / AGN?）、呼号抄错（QRZ?）
- 多个 HAM 在频率上并发活动

本步的延伸（后续迭代补齐，均已落地）：
- **两类虚拟 HAM**：会发 CQ 的呼叫台（占频点、可见）与只应 CQ 的应答台（不占频点、看不见），见 [虚拟 HAM 策略](./VIRTUAL-HAM.md) 的「两类虚拟 HAM」。
- **两个虚拟 HAM 自己通联**：`src/ham/hamQso.ts` + `QsoSession` 调度，操作者插不进去，且界面不给任何提示——真实情况下你也看不到别人是否在通联。
- **波段切片宽于瀑布窗口**（±25 kHz vs ±10 kHz，台站 12–18 个）：调谐找人，而不是读清单。

## 第四步：音频引擎

目标：加入音频，测试音频效果。

范围：
- 编码：文本 → CW 音频（700Hz / WPM / Farnsworth），HAM 发声（见 [音频与电磁环境](./AUDIO-ENVIRONMENT.md)）
- 解码输入：用户键控点划时序已由第二步产生，不再二次音频识别
- QSB / QRM / QRN 真实感：本步引入，可先简化

定位：音频是纯附加表现层，不改动任何逻辑（状态机、解析、HAM 生成不变）；HAM 文本报文 → CW 音频播放。

## 第五步：用户界面

目标：制作 UI 界面。

> **已完成（2026-10-14，2026-10-15 迭代为电台风格）**：外壳为常驻**电台面板**（频率/波段/模式 + 开台/关台电源 + 设置齿轮），二级视图为 **电台 / 日志 / 关于**，设置收进齿轮弹出的模态框；持久化与免责声明常驻。**开台 / 关台只控制"接收"**：虚拟 HAM 在应用启动时即在所有波段上活动，不随电源起落。界面细节见 [界面](./UI.md)。

约束：前四步均为无界面、可听 / 可测原型；UI 在第五步落地后，核心逻辑（状态机 / 解码 / HAM / 音频）一行未改，印证了"核心模块纯 TS、UI 只做呈现层"的架构。

## 设计要点与架构预留（跨步通用）

- **输入源抽象**：状态机的驱动源设计成可注入（用户输入 / HAM 输入 / 另一 HAM 输入），第一步即落实。
- **虚拟 HAM 接口**：单步原型里 HAM 即设计为可多实例对象；第一步用确定性脚本驱动，第三步扩展为随机生成与并发。
- **时钟与随机源可注入**是新模块的默认写法：依赖时间推进的逻辑不内部 `setTimeout`，而是接收 `now` 或注入 driver。状态机因此可以毫秒内跑完分钟级的长时段行为。
- **定时器清理**：所有真实定时器都在界面层，且由页面 / 会话在退出时显式停掉（`onLeave` / `dispose`）。
