# 开发路线（五步法）

> 本项目的开发分期与每步范围。技术栈见项目根目录 MEMORY.md（TypeScript + Vite + Vitest + Web Audio；**平台定为 Tauri（先 Web 原型、后打包 exe）**；**UI 已于 2026-10-14 实现**）。
> 策略：**自底向上、每层独立可验证**——先保证"大脑"（状态机）正确，再补输入（解码）、生成（HAM）、感知（音频）、外壳（UI）。
> 各能力域的设计见对应文档：[CW 编解码](./CW-PARSING.md)、[报文解析](./MESSAGE-PARSING.md)、[通联过程](./QSO-PROTOCOL.md)、[虚拟 HAM 策略](./VIRTUAL-HAM.md)、[音频与电磁环境](./AUDIO-ENVIRONMENT.md)、[UI 界面](./UI.md)。

## 第一步：文本直通状态机原型

目标：用 CW 报文的字母文本与一个虚拟 HAM 完成通话，专门验证 QSO 状态机能否正确解析各种输入。

范围与约束：
- 频率固定（单频道）、时间固定（无随机延迟）
- 无任何电磁环境（无 QSB / QRM / QRN）
- 用户输入以字母文本形式直接喂入，绕过摩斯解码与音频
- 虚拟 HAM 用确定性脚本驱动（固定应答逻辑，不随机）

本步实际落地三件套（不只是状态机）：
- 数据层：`data/dxcc.json` 加载 + 前缀 → 实体查表（展开 `prefixes`、首部子串匹配）
- 报文解析：文本 → `ParsedMessage`（见 [报文解析](./MESSAGE-PARSING.md)）：CQ 去重、呼号 ITU 格式 + 前缀表校验、RST 整 token 校验、省略呼号判断、BK / PSE K 处理、用户输入宽容容错
- QSO 状态机：7 状态 + 转移，消费 `ParsedMessage`（见 [通联过程](./QSO-PROTOCOL.md)）

必须实现并测试的逻辑：
- 状态机超时转移（EXCHANGE / SIGNOFF 的 5s 重发、首次呼叫 15s 无应答、HAM 3min 下线）；本步仅要求 HAM 行为确定性、不引入随机

测试用例（重点，验证"用户输入宽容"基线，参考真实 CW 通联）：
- 正常流：用户确认的 6 行序列（CQ → HAM 应答 → 用户 R+RST+BK → HAM R+RST+BK → 用户 R+TU73SK → HAM R+TU73SK）
- 异常流：抄错呼号（QRZ?）、RST 非法（UR RST?）、接收不全（? / AGN?）、超时无应答、K 与 BK 混用、呼号省略与误省、带 / 不带 R、CQ 三遍去重、操作后缀 /P /M /5、纯 K 结尾、SK 提前结束等

## 第二步：电键输入转文字（摩斯解码）

目标：实现摩斯解码，将用户电键（直键 / iambic / 键盘模拟）产生的点划时序转换为字母文本，接入第一步已完成的"文本 → 状态机"链路。

范围：
- 点划 / 时序 → 字母（见 [CW 编解码](./CW-PARSING.md) 的摩斯解码节：时序基准、符号判定、码表、容错）
- 支持 Farnsworth：放大字符 / 单词间隔而不改变点划基准速度
- 产出文本后，复用第一步的报文解析与状态机——第一步是第二步的上游依赖

边界：本步不涉及音频识别（用户键控直接产生时序事件，不经 FFT / 频谱）；音频渲染留到第四步。

## 第三步：多虚拟 HAM 与频率活动

目标：研究并实现虚拟 HAM 的生成机制，让多个虚拟 HAM 在同一频率（及多个频率）上活动。

范围：
- 呼号生成（B?7 > B?? > 地理 > 同洲 权重 + 随机后缀，见 [虚拟 HAM 策略](./VIRTUAL-HAM.md)）
- 运行时行为：CQ 节奏、应答延迟、接收不全（? / AGN?）、呼号抄错（QRZ?）
  - CQ 节奏与应答延迟**已落地**（2026-10-14）：`src/ham/activity.ts`，由界面层以 1 s 驱动循环推进；详见 [虚拟 HAM 策略](./VIRTUAL-HAM.md) 的「虚拟 HAM 运行时行为」
- 多个 HAM 在频率上并发活动

架构预留（原「本版不做」，**已于 2026-10-19 实现**）：
- 两个 AI HAM 之间也可通联，第三方插不进去。落地为 `src/ham/hamQso.ts` + `QsoSession` 调度，详见 [虚拟 HAM 策略](./VIRTUAL-HAM.md) 的「互相通联（后台）」。
- **对操作者不可见**：真实情况下看不到别人是否在通联，所以界面上没有任何标记或旁听入口；唯一的线索是调到那个频率后听到的报文。在这个频率上发 CQ 也不会被拒绝——那一对静默让位。
- 波段切片宽于瀑布窗口（±25 kHz vs ±10 kHz），台站 12–18 个：调谐找人，而不是读清单。

## 第四步：音频引擎

目标：加入音频，测试音频效果。

范围：
- 编码：文本 → CW 音频（700Hz / WPM / Farnsworth），HAM 发声（见 [音频与电磁环境](./AUDIO-ENVIRONMENT.md)）
- 解码输入：用户键控点划时序已由第二步产生，不再二次音频识别
- QSB / QRM / QRN 真实感：本步引入，可先简化

定位：音频是纯附加表现层，不改动任何逻辑（状态机、解析、HAM 生成不变）；HAM 文本报文 → CW 音频播放。

## 第五步：用户界面

> **已完成（2026-10-14，2026-10-15 迭代为电台风格）**：用**原生 TypeScript + Vite、零 UI 框架**实现。外壳为常驻**电台面板**（频率/波段/模式 `CW` + 开台/关台电源 + 设置齿轮），二级视图为 **电台 / 日志 / 关于**，设置收进齿轮弹出的模态框；持久化（IndexedDB 日志 + localStorage 设置），免责声明常驻。**开台 / 关台只控制"接收"**：虚拟 HAM 在应用启动时即在所有波段上活动，不随电源起落（见 [虚拟 HAM 策略](./VIRTUAL-HAM.md) 的「环境独立于用户电台」）。进度与遗留见仓库根 `STEP5-UI-NOTES.md`，技术选型把关见 `UI-TECH-REVIEW.md`。

目标：制作 UI 界面。

范围（见 [UI 界面](./UI.md)）：电台面板（频率 / 波段 / 模式 / 电源 / 设置齿轮）+ 电台页（调谐 + 波段活动 + 通联面板）/ 日志 / 关于，设置收进齿轮模态框；持久化（IndexedDB 日志 + localStorage 设置），免责声明常驻。

约束：前四步均为无界面、可听 / 可测原型；UI 在第五步落地后，核心逻辑（状态机 / 解码 / HAM / 音频）一行未改，印证了"核心模块纯 TS、UI 只做呈现层"的架构。

## 设计要点与架构预留（跨步通用）

- 输入源抽象：状态机的驱动源应设计成可注入（用户输入 / HAM 输入 / 另一 HAM 输入），第一步即落实；使第三步"多 HAM"与"AI 互连预留"零返工。
- 虚拟 HAM 接口：单步原型里 HAM 即设计为可多实例对象；第一步用确定性脚本驱动，第三步扩展为随机生成与并发。
- 频率字段：状态机 / 上下文预留 `frequency` 字段（第一步可固定单值），为第三步多频率活动铺垫。
- 超时与定时器：所有等待定时器（15s / 5s / 3min）在状态切换与上下文清空时清理（见 [通联过程](./QSO-PROTOCOL.md) 超时与重发规则的实现提示）。
