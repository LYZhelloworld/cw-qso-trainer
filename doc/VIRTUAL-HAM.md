## 呼号前缀表与地理位置

### 呼号前缀表

自行维护一份 JSON 表（静态资源，随应用打包）：

```json
{
  "BY": { "dxcc": "BY", "lat": 35.9, "lon": 104.2, "prefixes": ["BA", "BD", "BG", "BT", "BY", "BZ"] },
  "VR2": { "dxcc": "VR2", "lat": 22.3, "lon": 114.2, "prefixes": ["VR2"] },
  "JA": { "dxcc": "JA", "lat": 36.2, "lon": 138.2, "prefixes": ["JA", "JF", "JG", "JH", "JJ", "JK"] },
  "K":  { "dxcc": "K",  "lat": 39.8, "lon": -98.6, "prefixes": ["K", "W", "N", "AA", "AL"] },
  "DL": { "dxcc": "DL", "lat": 51.2, "lon": 10.4,  "prefixes": ["DA", "DB", "DC", "DD", "DE", "DF", "DG"] }
}
```

字段说明（与 [`../data/dxcc.json`](../data/dxcc.json) 的 `entities` 实际结构一致，每个实体仅四字段）：

| 字段 | 含义 |
|---|---|
| `dxcc` | DXCC 实体标记（如 `BY`/`JA`/`K`）；中立标识符，**非国家名、非 ISO 代码** |
| `lat` / `lon` | 参考经纬度（由 DXCC 实体质心近似推导，非精确位置） |
| `continent` | 由 `lat`/`lon` 启发式反推的粗略大洲标记（`AN`/`AF`/`EU`/`AS`/`NA`/`SA`/`OC`）；用于「同大洲」权重档，非国家 / 地区归属 |
| `prefixes` | 该实体拥有的呼号前缀数组；运行时展开为「前缀 → 实体」查表 |

> 上方示例 JSON 为 `data/dxcc.json` 中 `entities` 对象的精简示意（已省略顶层 `source` / `count` / `coordinate_note` 元数据，并略去 `continent` 以精简；实际数据含该字段）。去争议化：本表刻意**不入库** `country`、`cqZone`、`ituZone`、`region` 等字段——生成权重所需的「大洲」已预计算为 `continent` 字段（由 `lat`/`lon` 启发式推导、粗略近似），「距离」按坐标大圆计算、「数字区」（如 `BG7` 的 `7`）从呼号数字提取，二者运行时计算、不落地为字段，避免携带任何国家 / 地区归属信息。

> 注：世界上合法的呼号前缀（国家 / 地区标识）是**有限集合**，应枚举为完整列表，而非依赖宽松正则。呼号校验时，前缀必须命中此表，再结合 ITU 格式判定整体合法性：基本为「1–2 字母前缀 + 数字 + 1–4 字母后缀」，但中国允许 `B` + 数字的无后缀异地 / 便携形式（如 `B5`），且可带 `/P`、`/M`、`/5` 等操作后缀（见 [QSO 协议](./QSO-PROTOCOL.md) 的「用户呼号」一节）。完整前缀表已落地于 [`../data/dxcc.json`](../data/dxcc.json)，校验时只需判定「字母前缀是否命中该表」，**不记录其国家 / 地区归属**。

> 完整数据集已落地：[`../data/dxcc.json`](../data/dxcc.json)。生成脚本（从 RSGB 前缀列表 + ITU 网格生成）**不纳入仓库**，仅暂存在本地 [`../.workbuddy/staging/build-dxcc.py`](../.workbuddy/staging/build-dxcc.py)（含 `./sources/` 源文件），需要重跑时可用。该文件以 **DXCC 标记**为主键，每个实体仅含 `dxcc` / `lat` / `lon` / `prefixes` 四个字段——**刻意不存国家 / 地区名称与 ISO 代码**，以规避争议；坐标由国家质心近似推导、非实体精确位置。运行时所需的「前缀 → 坐标」查表应由该文件派生（展开 `prefixes` 数组后建立前缀到实体的映射）。

### 位置推断

- 根据呼号前缀推断
- 无法推断时，视为地理位置不可用
- 无法推断时，虚拟 HAM 生成概率均等

## 虚拟 HAM 生成策略

### 生成优先级

用户决定（以 `BG7XXX` 为例）：匹配到对方虚拟 HAM 的可能性由高到低为——

1. **同根前缀 + 同数字区**（`B?7`，如 `BA7` / `BD7` / `BG7` / `BT7` / `BY7` / `BZ7`）：最高
2. **同根前缀（任意数字区）**（`B??`，如 `B?1` / `B?9`）：次高，即同实体 / 同国家
3. **地理邻近**（跨实体，按大圆距离）
4. **同大洲**
5. **其他**

> 说明：数字区匹配**始终以「根前缀（首字母）」为作用域**——`B?7` 必为中国（B 系）台，不会跨实体去匹配其他国家同样带数字 `7` 的前缀。因此「同数字区」天然落在同根前缀内，**不会跨国家**；`B??`（同根前缀、任意数字区）即等价于同实体 / 同国家。对前缀本身已含数字者（如 `VR2`），其数字区由前缀固定，不参与「同数字区」比较。

权重示例：

```text
同根前缀 + 同数字区（B?7）：100
同根前缀（B??，任意数字区）：40
地理邻近 < 3000 km：10
同大洲：5
其他：1
```

### 生成算法

```text
function generatePeerCall(myCall, myLoc, prefixTable):
  candidates = []
  for each prefix in prefixTable:
    loc = prefixTable[prefix]
    weight = baseWeight(myLoc, loc)
    candidates.push({ prefix, weight })

  totalWeight = sum(candidates.weight)
  r = random(0, totalWeight)
  pick prefix by cumulative weight
  generate random suffix: 1 digit + 2–3 letters（前缀已含数字则只接字母）
  return full call
```

> `baseWeight` 按上方优先级与权重计算，并叠加距离权重（`< 3000 km` / `< 8000 km`）。其中「同大洲」由两实体 `lat`/`lon` 推导所属大洲后比较、「距离」由两坐标大圆公式计算，二者均不依赖任何国家 / 地区字段（与上方去争议化说明一致）。

### 呼号后缀生成

- 前缀确定后，随机生成后缀
- 例如 `BG7` 生成 `BG7XXX`，`JA` 生成 `JA1ABC`（后缀为随机字母，各次不同）
- 规则：随机追加「1 位数字 + 2–3 位字母」；前缀本身已含数字（如 `VR2`）则只接字母；低概率产出中国便携 `B5` 形式或 `/P`、`/M`、`/5` 等操作后缀

> 决策：虚拟呼号为练习用途，不校验是否真实存在、只判格式合法（见 [QSO 协议](./QSO-PROTOCOL.md) 的「用户呼号」）。因此后缀**纯随机生成**即可，无需为各地区维护精确格式，也**不**在前缀表 JSON 中新增 `suffixPattern` 字段——以维持 `data/dxcc.json` 仅四字段的去争议化纪律。

## 虚拟 HAM 运行时行为

> 实现（2026-10-14）：本节的 CQ 行为、应答延迟与活跃数量已落地于 `src/ham/activity.ts` —— 纯逻辑，时钟与随机源全部注入、模块内无定时器，因此「3 分钟无应答下线」这类长时段行为可在毫秒内完成测试。它由 `Frequency` 持有（一处存储，下线即从名单与排程同时移除），界面层 `QsoSession` 以 1 s 驱动循环调用 `advance()`。
>
> 一处实现细节不违背本节规格：新出现的台**首次**呼叫的延迟被有意设得比下方 30–60 秒的常态节奏更短，为的是调到新频段、或一台下线后补位时，不至于让用户对着静默等上一分钟；首次之后一律按本节间隔。
>
> **环境独立于用户电台（2026-10-15）**：频段活动不是「用户开机才有」。应用启动时**每个波段各自**生成 **5–9 个台**并立即开始各自的 CQ 节奏（界面层为每个波段持有一个 `QsoSession`，自带驱动、互不相干）。用户的**开台 / 关台**只决定「是否接收当前波段」：关台时不接话、不发声、不发射，但频段照常运转——到点仍呼叫、超时仍下线补位。因此「关台」不等于「清空」；同样地，切走波段再切回来，原波段仍是原来那批台。
>
> **台站有绝对频率（2026-10-15；2026-10-16 起对齐 1 kHz 网格）**：每个台生成时会被放置在一个**绝对频率**上——波段参考频率 ±9 kHz 之内、**对齐 1 kHz 网格**（7.010、7.011……），而不是相对拨轮的位置。1 kHz 是操作者实际使用的频率间隔，同时保证了「接收通带最宽也只有 500 Hz（还可再窄到 250 / 100 Hz）」时相邻两台不会被同时收到（见 [调谐与偏频](./AUDIO-ENVIRONMENT.md#调谐与偏频听到的音调)）；落点或呼号与同波段的台撞车时会重抽。这一个字段同时决定三件事：瀑布图上**画在哪里**（调谐时是窗口在动、台不动）、**听得清不清**（亮度/强度由它上报的 RST 推出）、以及**听不听得见**（超出拨轮 ±带宽/2 即被滤波器切掉）。

### 生成优先级（频段分布）

```text
同呼号数字区 > 同国家 > 同大洲 > 其他
```

### CQ 行为

- 每隔 **30 – 60 秒**随机发一次 CQ
- 连续 **3 分钟**无应答，下线
- 同一频段同时活跃 **5 – 9 个**，各自占一个 1 kHz 网格槽（波段参考频率 ±9 kHz 内共 19 个槽位，撞车会改落空槽；显式调用 `seedHams(n)` 时以 n 为补位目标）

### 应答延迟

- 用户发 CQ 后，第一台虚拟 HAM 随机延迟 **1 – 5 秒**开口；多台应答时的错开规则见下方「多人应答（堆叠）」
- 用户应答虚拟 HAM 的 CQ 后，对方随机延迟 **1 – 3 秒**再回复

### 接收不全

- 默认概率 **1% – 5%**，可调
- 触发时虚拟 HAM 发 `?` 或 `AGN?`（请求全文重发；`QRZ?` 专用于呼号抄错，不在此用）
- 要求用户全文重发
- 不模拟具体丢失内容

### 行为约束

- 虚拟 HAM 不会在后续阶段发 `PSE K`
- 虚拟 HAM 不会主动违反通联协议
- 用户发 `PSE K` 在后续阶段，虚拟 HAM 正常回应，不视为错误
- 虚拟 HAM 在呼号已确认、进入可省略阶段后，交还发言权一律用 `BK`（不用纯 `K`），向对方发出「可省略呼号」信号（见 [QSO 协议](./QSO-PROTOCOL.md) 的「收发基线」）
- 虚拟 HAM 回应 / 确认用户报文时，于报文起始加 `R`（收到确认）；例外：首次应答 CQ（给出本方呼号、建立通联）不带 `R`（见 [QSO 协议](./QSO-PROTOCOL.md) 的「收发基线」与「R（收到确认）」）

### 多人应答（堆叠）

> **已实现（2026-10-19）**：`src/ham/pileup.ts`（纯逻辑）+ `QsoSession` 调度。替换原先「第一版只允许一个台应答」的占位。

- 用户发 CQ 后，**2 – 3 台**先后应答；第一台仍在 **1 – 5 秒**内开口，后续各台在前一台报完呼号后再隔 **0.5 – 1.5 秒**，形成堆叠而不是齐射。
- **所有应答者都落在呼叫者的拨轮频率上**（CW 堆叠里大家零拍同一个目标），因此**不受 1 kHz 网格约束**；它们同时是瀑布图上的同一根亮柱。网格只约束波段上守听 / 自行呼叫的台。
- 每台报完自己的呼号后**静默 3 – 7 秒**再重呼，间隔各自独立抽取，用来把各台岔开（单声道音频一次只播一台）。
- **必须点名**：用户回复里出现某台的呼号，该台即为通联对象，其余各台离场；被点名者隔 1 – 3 秒回 `R UR RST 599 BK`，进入正常交换流程。
- **不点名不推进**：`R BK` 之类没有呼号的回复不会被任何一台认领，各台重新抽取静默后继续等待；界面会记一条「没有点名任何一台」。
- 每台最多重复 **4 次**；都没被点名则依次离场（为堆叠临时生成的台**下线**，原本就在波段上的台回到守听）。
- 关台时不发 CQ，也不会产生堆叠；堆叠状态不写入暂存，刷新即失去（已完成的通联不受影响）。

> **1 kHz 网格的边界**：网格约束的是「波段上的台落在哪个频率」，不是「应答者必须离你 1 kHz」。堆叠应答者按定义就在你的频率上，这正是它们会互相盖住、必须靠点名区分的原因。

### 互相通联（后台）

> **已实现（2026-10-19）**：`src/ham/hamQso.ts`（纯逻辑）+ `QsoSession` 调度。它取代了第三步留下的「两个 AI HAM 之间通联」预留（`planHamToHam` 仍保留，但不再是「未实现」的标记）。

- **随机发生**：每个波段每 **30 – 90 秒**尝试一次。前提是这一波段**至少 3 台**——两台互连，还要至少留一台给操作者；已在通联中的台不参与，优先挑一台**正在呼叫 CQ** 的台当呼叫方（现实里就是有人应了正在发的 CQ）。
- **同频**：应答方**调到呼叫方的频率**上，所以操作者只要把拨轮停在那一格，就能同时听到两边。这两台在通联期间不受 1 kHz 网格约束（网格约束的是「守听 / 自行呼叫的台」）；结束后应答方**回到自己原来的频点**，波段不会留下两台同频。
- **脚本**：就是 QSO 协议里的标准 **6 行**（CQ → 应答 → RST → RST → 73 → 73），按操作者设定的速度逐行播出，两次发射之间留 **0.6 – 1.6 秒**。
- **不能插话**：两台的 `inQso` 状态使它们不会成为「可通联对象」；把拨轮停在该频率时，「我发 CQ」按钮禁用（频率被占用），强行发送会被拒绝并说明原因。
- **可发现**：电台页「波段活动」单独一行列出 `A ↔ B`、频率与「调过去旁听」按钮；瀑布图标签与右上角显示这一对；两台的徽标写成「与 X 通联」，而不是笼统的「通联中」。
- **环境属性**：关台或切到别的波段时照常发生、照常推进脚本，只是听不到；操作者自己有通联或堆叠时**不插入**（单声道音频会互相切断）。通联不写入暂存，刷新后是新的一轮。
