# 报文解析（字母文本 → 结构化报文）

> 本文件负责把 CW 解码产出的**字母文本** → **结构化报文**（`ParsedMessage`）的语义解析，以及解析时用到的**呼号规格与校验**；产出供 [QSO 协议](./QSO-PROTOCOL.md) 的状态机消费。
> 上游：字母文本由 [CW 编解码](./CW-PARSING.md) 的摩斯解码层产出；下游：状态机见 [QSO 协议](./QSO-PROTOCOL.md)；虚拟 HAM 的生成与策略见 [虚拟 HAM 策略](./VIRTUAL-HAM.md)。

---

## 输入与输出

- 输入：一串大写字母文本（如 `CQ CQ CQ DE BG7XXX BG7XXX PSE K`），由摩斯解码层产出，已合并多余空格、统一大写。
- 输出：`ParsedMessage` 结构（见下）。

## 归一化规则

| 原始 | 归一化 |
|---|---|
| `5NN` / `5BN` / `VVN` 等短码 | `599` / `579` / `339` |
| `TNX` / `THX` | `TU` |
| `<SK>` | `SK` |
| 多空格 | 单空格 |
| 小写 | 大写 |

> 短码复原**只在能放 RST 的位置**做：`RST` 之后的一两个词，或者本身以数字开头的三位词（`5NN`、`5BN`）。整词都是短码字母的普通单词（`AND`、`TU`）不动——否则 `AND` 会被读成 `198`。短码表本身在 `src/message/macros.ts` 的 `CUT_NUMBERS`，这里反向用它，两张表不会走散。
>
> 归一化只处理「写法变体」，不改变语义；呼号本身不做归一化（保持用户所抄）。

## RST 格式与校验

合法 RST 是三位数字，每位独立约束：

```regex
^[1-5][1-9][1-9]$
```

- 第一位（可辨度）：1–5
- 第二位（强度）：1–9（不为 0）
- 第三位（音调）：1–9（不为 0）

示例（合法）：`599`、`589`、`579`、`5NN` → `599`、`5BN` → `579`、`VVN` → `339`（短码先经归一化复原）

不合法示例：`5999`（四位）、`ABC`、`59`（两位）、`5NNN`（归一化后仍非三位数字）

> **校验对象**：RST 是对**独立的 RST token** 校验，不是对整条消息。解析时先在分词后的消息 token 中找出**整 token 匹配**上述正则的那一个，才认定为 RST；消息中偶然出现的三位数字子串（如呼号里的数字）不会被误判。为避免 `5999` 这类被词边界 `\b` 部分命中，务必用「整 token 匹配」而非「消息内子串搜索」。

不合法时，虚拟 HAM 发：

```text
UR RST?
```

## 解析器输出结构

```typescript
interface ParsedMessage {
  to: string | null;        // 接收方呼号，或 "CQ"
  from: string | null;      // 发送方呼号
  type: "CQ" | "CALL" | "RST" | "END" | "QUERY" | "UNKNOWN";
  rst: string | null;       // 归一化后的 RST
  end: "PSE_K" | "K" | "BK" | "SK" | null;
  omit_calls: boolean;      // 是否省略了呼号
  callsignValid: boolean;   // 提取到的呼号是否通过格式 + 前缀表校验
  callsigns: string[];      // 提取到的全部呼号 token（不含 CQ、已对连续重复去重）
  raw: string;              // 原始文本
}
```

> `callsignValid` 由解析器在提取呼号 token 时即执行校验，状态机消费时直接读取，无需重复校验。

## 解析流程

```text
1. 归一化（大写、合并空格、5NN/TNX/<SK> 折叠）
2. 识别结束符：PSE K → BK → SK → K（顺序有意义，先长后短）
3. 移除 DE
4. 提取呼号 token 并逐个校验；连续重复的同一呼号只留一个；CQ 单独记一个标志
5. 根据上下文判断 to / from（含省略呼号的推断）
6. 识别消息类型
7. 处理 BK：记录「用户使用过 BK」（省略资格的唯一判据仍是 callsignsConfirmed）
8. 返回 ParsedMessage
```

几个容易写错的地方：

- **结束符顺序**：必须先测 `PSE K` 再测单独的 `K`，否则 `PSE K` 会被当成 `K` 且留下一个 `PSE` 词。
- **`CQ` 不进 `callsigns`**：`CQ` 不是呼号，它只置一个标志。否则 `CQ CQ CQ DE BG7XXX` 会得到 `to = CQ, from = CQ`。
- **连续重复去重**：`DE BG7XXX BG7XXX` 里同一呼号重复两次，只留一个，否则会被误判成「接收方 + 发送方」两个不同的人。
- **`type` 的判定顺序**：有合法 RST → `RST`；有 `RST` 字样但没有合法 RST → `QUERY`（即 `UR RST?`）；有结束语或 `end === SK` → `END`；有 `QRZ?` / `AGN?` / `?` → `QUERY`；有 `CQ` → `CQ`；有呼号 → `CALL`。
- **`RST` 后面的数字不是呼号**：见下方「比赛交换数字」。

> 实现见 `src/message/parse.ts`（`normalize` / `parseMessage`）。它不碰 DOM、不碰存储，用注入的 `DxccDatabase` 做前缀校验，因此可以单测。

## 比赛交换数字

比赛报文里 `RST` 后面还挂着交换数字：`JA1ABC 5NN 24`、`R 5NN TTA`。这些 token **不能进 `callsigns`**——`24` 会被前缀规则误判成某种呼号，`U4`（`24` 的短码写法）更会被读成一个"数字打头的合法呼号"，于是状态机以为报文里出现了第三方的呼号，回一句 `QRZ?`。

规则只有一条，按位置而不是按内容：

- **`RST` 记号之后最多两个 token，只要读起来像数字，就当作交换数字**（写进 `msgTokens`，不参与呼号提取）。两个是为了同时容纳分区与序号（序号短码之后仍是一个词位，多出来的第二个位置留给重发时连发的那个号）；再多就回到正常分词。
- **"读起来像数字"= 全数字，或者全由短码字母与数字组成**（`T5`、`U4`、`TTA`）。所以 `RST 599 N9N` 里的 `N9N` 也会被读成 `999`。这个取舍靠得住，是因为**交换信息从不单独发**：比赛中它永远跟着报告一起发（`5NN T4A`、`5NN 041`），所以「合法 RST 之后」正好是数字该在的位置，不必凭形状去猜。代价是"报告后面紧跟一个恰好长得像短码的呼号"认不出来（`N9N`、`T4A`），而那种写法在实战中不会出现。
- 反过来，**前面没有报告时同一个 token 仍按呼号读**（`T4A` 单独出现会被当成呼号）——这是位置规则的边界，也是上一条取舍的另一面。
- 只在**已经出现合法 RST** 之后生效，所以日常报文里跟在报告后面的词仍按原规则处理。
- **呼号的识别不受影响**：给会话侧另外提供 `namedCallsignsIn(line)`——只取"长得像呼号且命中前缀表"的 token，堆叠点名与「这条报文在叫谁」都用它，不再复用整条 `parseMessage` 的 `callsigns`。

> 交换数字本身的含义（分区 / 序号、补位、短码）见 [比赛模式](./CONTEST.md)；短码复原规则见上方「归一化规则」。

## 呼号省略处理

- 若报文无呼号，且 `callsignsConfirmed` 或 `callsignsOmitted` 为真：
  - 用户发送：`to = peerCall`，`from = myCall`
  - 对方发送：`to = myCall`，`from = peerCall`
- `BK` 后用户仍可带呼号，不视为错误
- 只要双方呼号已明确，可随时省略呼号
- 省略资格的唯一判据是 `callsignsConfirmed`（见 [QSO 协议](./QSO-PROTOCOL.md)）

## 用户发 PSE K 的处理

- 用户在后续阶段发 `PSE K` 不视为错误
- 虚拟 HAM 正常回应
- 虚拟 HAM 自身不会在后续阶段发 `PSE K`

## 用户呼号

用户呼号是**练习用的呼号**，只判格式、不查真伪；它同时也是虚拟 HAM 生成的权重基准（见 [虚拟 HAM 策略](./VIRTUAL-HAM.md)）。

- 必须填写，统一大写
- 允许虚拟格式，如 `BG7XXX`、`B5`
- 不校验呼号是否在现实中存在
- 校验分两步：先符合 **ITU 呼号格式**，再确认前缀命中**枚举的前缀表**（`data/cty.dat`）
- 允许 `/P`、`/M`、`/QRP`、`/5` 等操作后缀
- **只判定格式合法性，不记录、不展示该呼号属于哪个国家 / 地区**（延续去争议化原则）

### ITU 呼号格式

ITU 呼号由「国家 / 地区前缀 + 数字 + 后缀」构成，分两种基本格式：

- 格式一：1 个字符 + 1 位数字 + 1–4 个字母的后缀
- 格式二：2 个字符 + 1 位数字 + 1–4 个字母的后缀

约束：

- 前 1–2 个字符是国家 / 地区标识（如中国为 `B`）
- 中国的典型结构为 `B` + 电台种类字母 + 分区数字 + 后缀，例如 `BG5ABC`
- 后缀由字母组成，最多 4 个；部分国家用后缀首字母 / 长度区分执照等级（如澳大利亚标准呼号后缀为 3 字母，首字母限 H / L / M / N / P / V）
- 呼号后可加 `/` + 操作状态标识（`/M` 移动、`/P` 便携、`/AM` 航空移动、`/MM` 海上移动，以及 `/5` 这类分区数字），这不是呼号本身的一部分
- 禁止使用可能被误认为遇险信号的组合（例如以数字开头且第二字符为 `O` 或 `I`）

### 中国异地 / 便携呼号（易漏写的情况）

- 美国 / 日志类呼号用**后缀**表示异地，例如 `W1AW/5`（在 5 区操作）。
- 中国用**前缀**表示异地：在 `B` 后直接跟分区数字，**可省略后继字母后缀**，例如 `B5`、`B1`。`B` + 数字 也属合法（虽少见）。
- 因此 `B5`、`B1`、`B5ABC` 这类「`B` 起头、数字后无（或少量）字母」的呼号同样是合法的，校验时不应判为非法。
- 注意：这与 `/5` 后缀式是**同一语义的不同写法**，两者都允许；本项目只判格式合法，不区分、不记录其国家 / 地区。

### 呼号正则

```regex
^[A-Z]{1,2}[0-9][A-Z]{0,4}(/[A-Z0-9]{1,4})?$
```

> 后缀字母改为可选（`[A-Z]{0,4}`），以容纳中国 `B5` 这类无后继字母的异地 / 便携呼号；`/` 操作后缀（如 `/P`、`/M`、`/QRP`、`/5`）仍允许。

示例（均合法）：

- `BG7XXX`（中国，标准）
- `B5`（中国，异地 / 便携，无后缀）
- `B1`、`B5ABC`（中国，`B` + 数字，少见但合法）
- `JA1ABC`（日本）
- `VR2XXX`（香港特别行政区）
- `W1AW`（美国）
- `BG7XXX/P`、`JA1ABC/QRP`、`W1AW/5`（带操作后缀）

### 呼号合法性校验

对每个非 `CQ` 的呼号 token 执行两步校验：

1. **ITU 格式**：匹配上方正则（后缀字母可选、`/` 操作后缀允许）。
2. **前缀表命中**：从呼号提取「字母前缀」（**首个数字前的字母**，并先去掉 `/...` 操作后缀），该字母前缀必须命中 [`data/cty.dat`](../data/cty.dat) 的 `prefixes` 全集。判定方向有三个：精确等于某个 token；某个 token 以它开头（`B` → `BA` / `BD` / …）；它以某个 token 开头（`KA` → `K`——文件列的是呼号开头，`K` 一条就覆盖了全部 `K*`）

- 两步都通过 → `callsignValid = true`。
- 任一不通过（如杜撰前缀 `QQ1ABC`、格式非法）→ `callsignValid = false`。
- 状态机据此判断：若已确认 `peerCall` 而本条呼号非法、或出现了第三方的合法呼号，均计 `CALL` 重试并发 `QRZ?`——**切勿误当作「省略呼号」处理**，否则会掩盖用户的抄号错误。
- 收紧后的正则同时排除了 `599` 这类全数字被误判为呼号的情况。

> 前缀表从哪来、坐标怎么取、为什么要去掉国家 / 地区字段，见 [虚拟 HAM 策略](./VIRTUAL-HAM.md) 的「呼号前缀表与地理位置」。
